## 並走の結果

- `/api/state` の比較: 15:54 から 2 時間 25 分、1,749 回比べ、違い（同じ JSON のパスが 70 秒以上違うもの）は 0 件。取得のエラーも 0 件。
- `agent_status`（ペインごとの遷移の列）: 両方で 184 件ずつ、すべて一致。WS のつなぎ直しは 0 回。携帯からの書き込み（起動、Clear、Stop など）が始まった後も一致していた。
- Go 版の資源（2 時間 37 分の時点）: RSS 17.7 MB（最大 31.9 MB）、スレッド 38、fd 11。2 時間の時点からほぼ変わらない。参考までに、Node 版は RSS 76.7 MB。

## 実機で確かめたこと（4b）

利用者が携帯から Go 版に対して確かめ、問題はなかった: 数字キーでの選択、送信が 1 回で確定すること、手で打った下書きが混ざらないこと、画面全体を使うペインのスクロール、完了の印・ブランチ・日本語の表示、agent の起動（profile の選択を含む）、Stop と Clear、Home の件数と profile ごとの一覧、スリープや電波が切れた後のつなぎ直し。起動、Clear、Stop が Go 版を通ったことは、Go 版の `pane-profiles.json` で確かめた（Node 版の記録は変わっていない）。worktree のブランチの切り替えには、両方の bridge が同じように追従した。

## 未確認のまま、利用者の判断で進めたこと

- 長く動かしたときのメモリ、スレッド、fd の傾き（測ったのは 2 時間 37 分まで）
- 夜のスリープからの復帰（機械のスリープをはさむ並走はしていない）
- 試験用 orchestrator での CLI のアカウント判定（許す側）と worktree の削除（計画 4b の 4。§5.5 の「許す側」を含む）
- 信頼していないディレクトリで起動したときの `blocked` と、最初の依頼が保留されること（§5.4）

切り替えの後は、orchestrator が Go 版の `agentwebctl` を本番で使うので、CLI のアカウント判定は普段の使い方の中で通る。資源の傾きとスリープからの復帰も、本番の bridge で見ていく。

## 計画からずれたこと

- 4b を、4a の 3 日を待たずに 4a と重ねて始めた（利用者の判断）。両方の bridge は同じ herdr を見ているので、比較は続けられた。
- 4b の 3（本番の `pane-profiles.json` を Go 版にコピーして起動し直す）はしなかった。本番の記録はどれも既定の `claude` で、記録がないときの Go 版の選び方（`profileForAgentType`）でも同じ profile になるため。切り替えの後は Go 版が本番の state を使うので、この記録をそのまま引き継ぐ。

## セキュリティの不変条件

退行は見つかっていない。§5.5 のサーバー側の項目（`/api` と `/ws` の全ルートでトークンが要ること（`/healthz` と静的ファイルは意図して公開している）、loopback での待ち受け、静的ファイルの範囲、transcript の範囲、アカウントが不明なときの拒否、`launch_profiles` の許可リスト）と、action の出力にトークンを出さないことは、CI のテストで通っている。CLI のアカウント判定の許す側は、上のとおり未確認。
